# День 21 — Индексация документов

## Задание

Взять набор документов (README / статьи / код / pdf), минимум 20–30 страниц
текста или эквивалент в коде. Реализовать пайплайн индексации: разбиение
на чанки, генерация эмбеддингов, сохранение индекса. Усиление: метаданные
к каждому чанку и минимум две стратегии chunking со сравнением.

## Корпус

Сам репозиторий: README всех двадцати дней, документы из `docs/`, сценарии
видео и общий код `shared/*.py`.

| Что | Файлов | Знаков |
|---|---|---|
| markdown (README, docs, сценарии) | 37 | 159 243 |
| python (`shared/*.py`) | 10 | 196 191 |
| **итого** | **47** | **357 223** |

**≈198 страниц** по 1800 знаков — против требуемых 20–30.

Выбор не от лени. Корпус разнородный: markdown размечен заголовками,
python — определениями верхнего уровня, и структурная нарезка обходится
с ними по-разному. А главное — я знаю, где лежат правильные ответы, и могу
честно проверить, находятся ли они. На скачанных статьях разметку пришлось
бы придумывать на глаз, и сравнение стратегий превратилось бы в «мне
кажется».

```bash
python3 corpus.py       # что попадёт в индекс и сколько это страниц
```

## Эмбеддинги без зависимостей

У DeepSeek эндпоинта `/embeddings` нет — отвечает 404. У OpenRouter есть:
`openai/text-embedding-3-small`, 1536 измерений. Всё через `urllib`,
`requirements.txt` остаётся пустым.

Векторы лежат в SQLite как BLOB из float32, косинусная близость считается
вручную — на нашем масштабе (840 векторов) это миллисекунды, FAISS не нужен.

**Кэш — не украшение.** Корпус индексируется двумя стратегиями, у них много
общих кусков, а на отладке индекс пересобирался десятки раз. С кэшем
повторная сборка идёт по диску:

```
первый проход:  1.69с
второй проход:  0.002с   (векторы те же до бита)
```

Ключ кэша — `sha256(модель + текст)`, поэтому смена модели обнуляет кэш сама,
без ручной чистки.

## Две стратегии нарезки

| | `fixed` | `structural` |
|---|---|---|
| границы | окно 1200 знаков, перехлёст 200 | заголовки `##`, определения `def`/`class` |
| кусков | 375 | 465 |
| средняя длина | 1125 | 765 |
| медиана | 1192 | 558 |
| от … до | 218–1199 | 130–1879 |
| разброс | ±209 | ±504 |
| `section` в метаданных | `знаки 2964–4160` | `Главные грабли: macOS не пускает…` |

У `fixed` куски ровные и предсказуемые по цене, но он не знает о тексте
ничего и режет посреди слова — в выдаче это видно как кусок, начинающийся
с «ова, артефакт #10». У `structural` куски осмысленные, зато разной длины.

**Метаданные** у каждого куска: `source`, `title`, `section`, `chunk_id`,
плюс номер по порядку, смещение и длина. Без них результат поиска —
безымянный кусок текста, по которому не понять, можно ли ему верить.

## Сравнение: по числу кусков ничего не понять

Количество и средняя длина не говорят, находится ли нужное. Поэтому
сравнение сделано на поиске: 14 вопросов, у каждого известен файл, где
ответ заведомо есть. Вопросы заданы словами, которых в документах нет
дословно, — иначе проверялось бы совпадение подстроки, а не смысл.

```bash
python3 compare.py        # таблица
python3 compare.py -v     # плюс что именно нашлось
```

| стратегия | hit@1 | hit@3 | MRR |
|---|---|---|---|
| `fixed` | 4/14 | 8/14 | 0.449 |
| `structural` | **10/14** | **12/14** | **0.774** |

Разница MRR **+0.325** в пользу структурной нарезки. MRR взят потому, что
чувствителен не только к факту попадания в тройку, но и к тому, насколько
высоко стоит правильный ответ.

**Почему structural выигрывает.** Кусок, совпадающий с разделом, говорит
об одном. Окно фиксированного размера склеивает конец одной темы с началом
другой, вектор усредняется и перестаёт отвечать на конкретный вопрос.
Видно на примере: на запрос «почему сжатие бывает дороже» structural даёт
0.547 и раздел «Сжатие стоит денег, и это видно отдельной строкой», fixed —
0.415 и «знаки 990–2185».

## Где поиск промахивается у обеих стратегий

Два вопроса из четырнадцати не находятся ничем, и это не дефект индекса —
нужные файлы в нём есть, я проверил. Пример:

> «Какими сообщениями обмениваются при установлении связи по стандартному
> вводу-выводу?»

Промах. Добавляем одно слово:

> «Какими сообщениями обмениваются при рукопожатии **MCP**?»

Нужный файл поднимается на 2-е место. Вопрос, сформулированный вообще без
технических терминов, смысловой поиск по русскому тексту не вытягивает:
модель англоцентричная, и связь «стандартный ввод-вывод» → `stdio` она
не держит. Полезный предел, о котором стоит знать до того, как строить
на таком поиске что-то серьёзное.

## Оговорки честности

**Структурная нарезка не бывает чисто структурной.** Раздел на пять тысяч
знаков — плохой кусок: вектор размазывается по десятку тем. Поэтому длинные
разделы всё равно дробятся, но имя раздела сохраняется у всех частей
(`Agent (10/34)`). Без этого потолка structural проиграл бы.

**Четыре куска из 465 выходят за потолок на 2–5%** (1879 при 1800). Это
следствие склейки коротких хвостов: иначе последняя строка `@dataclass`
уезжала в индекс отдельным куском на десять знаков. Гонять хвост обратно
через резку значит плодить новый хвост и зацикливаться.

**Чего тут нет:** превращения PDF в текст. Корпус уже текстовый, и шаг
`pdf → текст` не понадобился. Подмена корпуса — один файл `corpus.py`,
остальное от источника не зависит.

## Что видно в окне

Один запрос — две колонки выдачи. Слева `fixed`, справа `structural`,
у каждой находки оценка, источник, раздел и `chunk_id`. Кнопка «Сравнить
стратегии» прогоняет все 14 вопросов: в таблице место нужного источника
по каждому вопросу, снизу hit@1, hit@3 и MRR.

## Мелочи, которые всплыли в работе

**Заголовки HTTP кодируются latin-1.** `X-Title: AI Advent — индексация`
валил запрос с `UnicodeEncodeError` на тире. В заголовках только ASCII.

**Кириллица в имени shell-переменной** не работает: `КОРПУС="..."` bash
понимает как попытку запустить команду с таким именем.

**Индекс и кэш уважают `AI_ADVENT_MEMORY_DIR`** — тот же каталог, что у
истории диалогов. Иначе приложение писало бы базы внутрь `.app` и теряло
кэш при каждой пересборке.

## Запуск

```bash
cd days/day-21-indexing

python3 corpus.py                      # состав корпуса
python3 build.py                       # собрать обе стратегии
python3 build.py --stats               # что уже собрано
python3 search.py --both "ваш вопрос"  # поиск, две выдачи рядом
python3 compare.py                     # сравнение на 14 вопросах
python3 web.py                         # http://127.0.0.1:8000
./build_app.sh && open "dist/День 21.app"
```

Нужен `OPENROUTER_API_KEY` в `.env`. Полная сборка корпуса с нуля стоит
около **$0.006**; повторная — копейки, почти всё берётся из кэша.
