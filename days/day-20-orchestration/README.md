# День 20 — Оркестрация: три MCP-сервера в одном чате

## Задание

Зарегистрировать несколько MCP-серверов. Сделать так, чтобы агент выбирал
нужный инструмент, корректно маршрутизировал запросы и выполнял длинный флоу.
Проверить сценарий с инструментами с разных серверов и корректность выбора
и порядка вызовов.

## Что сделано

Подключены три сервера, написанные в предыдущие дни. Не скопированы —
запущены как есть:

| Сервер | Откуда | Область | Инструментов |
|---|---|---|---|
| `git` | день 17 | факты о репозитории: коммиты, дни, файлы, GitHub | 6 |
| `sched` | день 18 | фоновые задачи по расписанию | 7 |
| `pipe` | день 19 | конвейер: найти → сжать → сохранить | 6 |

Итого **19 инструментов в одном списке**. Кнопок «вызвать search» в окне нет:
инструмент выбирает агент в чате, как и просил заказчик.

## Главная трудность — не подключить, а не перепутать

`MCPToolset` умел несколько серверов с 17-го дня, подключение заняло три
строки. Настоящая работа началась там, где областей стало три, а инструментов
девятнадцать.

**Пересекающиеся инструменты.** `git__search_commits` и `pipe__search` оба
ищут по репозиторию. Разница содержательная: первый отвечает на вопрос,
второй готовит данные для сжатия. Модель без подсказки берёт `pipe__search`
на вопрос «найди коммиты про MCP» — и вместо ответа запускает конвейер.

Лечится не намёком, а прямым правилом в системном промпте
([routing.py](routing.py)):

> Спрашивают факт о репозитории — бери `git__*`. Конвейер для этого не нужен:
> `pipe__search` существует, чтобы готовить данные для сжатия и записи,
> а не чтобы отвечать на вопросы.

Карта маршрутов лежит в одном модуле и уезжает и в окно, и в CLI — иначе
проверка проверяла бы не то, что работает в приложении.

## Проверка выбора и порядка

Задание требует проверить корректность машинно, поэтому у каждого сценария
есть ожидание ([flow.py](flow.py)):

```python
servers  # какие серверы обязаны участвовать
expect   # инструменты, которые обязаны быть вызваны
order    # те, чей ОТНОСИТЕЛЬНЫЙ порядок важен
forbid   # инструменты, которых быть не должно (взял не тот сервер)
```

```bash
python3 flow.py          # все пять сценариев
python3 flow.py 5        # только длинный флоу
```

Результат прогона — 5 из 5:

| № | Сценарий | Маршрут | Итог |
|---|---|---|---|
| 1 | факт о репозитории | `git__commits_by_day` | ✓ |
| 2 | фоновые задачи | `sched__list_tasks` | ✓ |
| 3 | похожие инструменты на разных серверах | `git__search_commits` | ✓ |
| 4 | нужен файл — значит конвейер | `pipe__search` ×3 → `summarize` → `save_to_file` | ✓ |
| 5 | длинный флоу через три сервера | `git` → `pipe` → `pipe` → `pipe` → `sched` | ✓ |

## Почему порядок проверяется относительный, а не точный

Пятый сценарий в разных прогонах даёт разную последовательность:

```
прогон А:  git__repo_stats → pipe__search → pipe__summarize → pipe__save_to_file → sched__add_task
прогон Б:  git__repo_stats → pipe__search → pipe__summarize → sched__add_task → pipe__save_to_file
прогон В:  git__repo_stats → pipe__search → sched__add_task → pipe__summarize → pipe__save_to_file
```

`sched__add_task` гуляет по середине. И это правильно: завести задачу
не зависит от выжимки, порядок между ними не важен. А вот `search →
summarize → save_to_file` держится во всех прогонах — потому что там
зависимость по данным, номер артефакта.

Поэтому проверка требует относительного порядка внутри зависимой цепочки
и молчит про независимые части. Требовать точного совпадения списка значило
бы ловить модель на том, что ошибкой не является.

**Сценарий 4 сделал три поиска подряд** вместо одного: уточнял запрос
(`планировщик scheduler` → `scheduler` → `sched`). Тоже не ошибка — лишний
вызов инструмента дешёвый, а порядок зависимой цепочки сохранён.

## Проверялка, которая умеет говорить «нет»

Проверка, всегда отвечающая «✓», бесполезна. Поэтому у неё свой тест
на подложенных журналах вызовов, без участия модели:

```bash
python3 test_checks.py
```

```
✓ не тот сервер: вместо git пошёл в pipe         вердикт False (ждали False)
✓ порядок нарушен: сжал раньше, чем нашёл        вердикт False (ждали False)
✓ шаг пропущен: не сохранил в файл               вердикт False (ждали False)
✓ инструменты не вызывались вовсе                вердикт False (ждали False)
✓ лишний повтор порядок не рушит                 вердикт True  (ждали True)
✓ чужой вызов в середине цепочки не мешает       вердикт True  (ждали True)

проверялка ошиблась в 0 случаях из 7
```

## Что видно в окне

Сверху — три сервера с областями ответственности и пять готовых сценариев
кнопками. Справа — панель **«Маршрут»**: каждый вызов пронумерован и окрашен
по серверу, поэтому переход `git → pipe → sched` виден как смена цвета.
Под маршрутом — результат машинной проверки, если запрос пришёл из сценария.

Цвета: `git` оранжевый, `sched` синий, `pipe` зелёный.

## Мелочи, которые всплыли в работе

**Три сервера внутри .app — три отдельных процесса.** Приложение поднимает
их как дочерние:

```
server_git.py
server_sched.py
server_pipe.py
```

Серверы не переписаны под бандл: `build_app.sh` копирует те же файлы из папок
дней 17–19 под разными именами, а `routing.py` сначала ищет их рядом с собой
и только потом в репозитории.

**`pgrep -f 'День 20'` не находит приложение.** В командной строке процесса
стоит путь к `Python.framework`, а не имя бандла. Из-за этого я снял не тот
процесс и минуту смотрел на приложение дня 19, гадая, почему у него один
сервер вместо трёх. Надёжный способ — искать порт через `lsof`, а дочерние
серверы через `pgrep -P <pid>`.
