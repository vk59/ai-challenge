# День 16 — Подключение MCP

## Задание

Установить MCP SDK/клиент или поднять MCP-сервер, написать минимальный код,
который устанавливает соединение и получает список доступных инструментов.
Проверить, что соединение устанавливается и список возвращается корректно.

## Сначала — про слово «сервер»

Никакой аренды, хостинга и VPS. **MCP-сервер поверх stdio — это обычный
процесс на вашей же машине.** Клиент запускает его как дочерний и общается
через stdin/stdout. Ни одного сетевого соединения.

Слово «сервер» здесь в смысле «тот, кто обслуживает запросы», а не «железка
в дата-центре».

## Протокол целиком помещается в голову

MCP поверх stdio — это JSON-RPC 2.0, по одному JSON-объекту на строку.
Рукопожатие из трёх шагов:

```
→ {"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}
← {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18",...}}
→ {"jsonrpc":"2.0","method":"notifications/initialized"}
      (уведомление — ответа не будет)
→ {"jsonrpc":"2.0","id":2,"method":"tools/list"}
← {"jsonrpc":"2.0","id":2,"result":{"tools":[...]}}
```

Это не пересказ документации, а настоящий вывод `list_tools.py --raw`.

## Почему без SDK

В репозитории пятнадцать дней подряд ноль внешних зависимостей: `llm.py`
написан на `urllib`, а не на `requests`, хранилище — на `sqlite3` из
стандартной библиотеки. Клиент MCP туда же: [shared/mcp.py](../../shared/mcp.py),
269 строк, только stdlib.

Причина не в аскезе. Протокол простой, и когда он написан руками, на видео
видно сам протокол, а не обёртку над ним.

`requirements.txt` после этого дня **по-прежнему пустой**.

## Но тогда как доказать, что это настоящий MCP

Если написать и клиент, и сервер самому, они «договорятся между собой»,
и это ничего не докажет. Поэтому клиент проверен на **чужой реализации** —
официальном `mcp-server-time` от Anthropic:

```
  ✓ соединение установлено
    сервер:      mcp-time 1.30.0 · протокол 2025-06-18
    протокол:    2025-06-18 (совпал с нашим)
    возможности: experimental, tools

  ✓ инструментов получено: 2

    1. get_current_time
       Get current time in a specific timezone
       · timezone: string — обязательный

    2. convert_time
       Convert time between timezones
       · source_timezone: string — обязательный
       · time: string — обязательный
       · target_timezone: string — обязательный
```

И вызов работает:

```
  Пробный вызов: get_current_time({'timezone': 'Europe/Moscow'})
  ← {"timezone": "Europe/Moscow", "datetime": "2026-09-28T01:40:23+03:00", ...}
```

Официальный сервер поставлен в отдельный `.venv` рядом — это **зависимость
проверки, а не зависимость кода**. Клиенту он не нужен, и в git этот venv
не попадает.

## Свой сервер: память агента наружу

[server.py](server.py) отдаёт по MCP то, что агент накопил за дни 7–15.
Тоже stdlib, тоже без зависимостей:

| инструмент | что отдаёт |
|---|---|
| `list_chats` | сохранённые диалоги: имя, число пар, дата |
| `recall` | долговременную память: профиль, решения, знания |
| `task_state` | этап задачи, шаг, отметки, журнал переходов |
| `invariants` | ограничения проекта из дня 14 |

Живой вызов:

```
  task_state({"session": "импорт-1с"}) →
      Диалог «импорт-1с»
      этап: выполнение
      цель: Импорт остатков из 1С
      шаг: пишем парсер выгрузки
      отметки: plan_approved
      пройдено: планирование → выполнение
```

Это замыкает весь репозиторий: пятнадцать дней агент копил состояние,
теперь оно доступно любому MCP-клиенту — нашему, Claude Desktop, какому
угодно.

## Три места, где спотыкаются

**Уведомление — не запрос.** У `notifications/initialized` нет `id`, и
ответа на него не будет никогда. Если клиент станет его ждать, он зависнет
навсегда. В `_request` ответ ищется строго по своему номеру, а уведомления
отправляются через отдельный `_notify`.

**В stdout сервера — только протокол.** Один лишний `print` ломает разбор
у клиента. Всё, что сервер хочет сказать человеку, идёт в stderr. В клиенте
stderr вычитывается отдельным потоком — иначе буфер однажды заполнится
и сервер встанет намертво посреди работы.

**Ошибка инструмента — не ошибка протокола.** Когда `task_state` зовут без
обязательного параметра, правильный ответ — результат с `isError: true`,
а не JSON-RPC-ошибка. Иначе клиент решит, что сломался сервер:

```
  task_state({})        → isError=True  Ошибка: нужно имя диалога в параметре session
  нет_такого({})        → isError=True  Ошибка: нет такого инструмента: нет_такого
```

## Запуск

```bash
cd days/day-16-mcp

python3 list_tools.py                   # свой сервер, память агента
python3 list_tools.py --raw             # показать сырой JSON-RPC
python3 list_tools.py --call            # ещё и вызвать инструмент
python3 list_tools.py -- <любая команда> # произвольный сервер
```

Чтобы проверить на официальном сервере (нужен один раз):

```bash
python3 -m venv .venv
.venv/bin/python -m pip install mcp-server-time
python3 list_tools.py --server time
```
