# День 26 — Локальная LLM

## Задание

Установить и запустить любую локальную LLM. Проверить, что модель
запускается локально, к ней можно обратиться через CLI или HTTP API
и она отвечает на простой запрос. Сделать минимум три запроса разной
сложности.

## Что поставлено

**Ollama 0.35.1** через `brew install ollama`. Выбран потому, что даёт
сразу три способа обращения и ничего не надо компилировать:

| способ | адрес | зачем |
|---|---|---|
| CLI | `ollama run qwen2.5:3b "..."` | быстро проверить руками |
| родной HTTP API | `POST /api/generate` | даёт `eval_count` и тайминги |
| **OpenAI-совместимый** | `POST /v1/chat/completions` | весь наш код заработал без изменений |

Третий пункт и решил дело. В `shared/llm.py` добавлен провайдер `LOCAL` —
отличается только адресом и тем, что ключ не нужен:

```python
LOCAL = Provider(
    "Local", "http://127.0.0.1:11434/v1", "OLLAMA_HOST",
    "https://ollama.com/download", needs_key=False, local=True,
)
```

Заодно пришлось сделать заголовок `Authorization` условным: посылать
`Bearer ` с пустым значением — приучать себя к мусору.

Машина: MacBook с M4 Pro, 48 ГБ памяти. Модели:

| модель | размер | квантизация |
|---|---|---|
| `qwen2.5:3b` | 1.9 ГБ | Q4_K_M |
| `qwen2.5:7b` | 4.7 ГБ | Q4_K_M |

Брал Qwen, а не Llama, из-за русского языка: вопросы и документация
в проекте русские.

## Шесть запросов разной сложности

Задание просит минимум три — сделано шесть, и у каждого есть **машинная
проверка**. Без неё «модель отвечает» значит только «что-то написала».

```bash
python3 probe.py                      # локально
python3 probe.py --cloud              # то же в облаке
python3 probe.py --model qwen2.5:7b
python3 probe.py --cold               # с замером холодного старта
```

| # | запрос | сложность | 3B | 7B | облако |
|---|---|---|---|---|---|
| 1 | факт одним словом | простое | ✗ | ✓ | ✓ |
| 2 | следование формату JSON | простое | ✓ | ✓ | ✓ |
| 3 | арифметика в три шага | среднее | ✓ | ✓ | ✓ |
| 4 | убрать канцелярит | среднее | ✓ | ✓ | ✓ |
| 5 | код по описанию | сложное | ✓ | ✓ | ✓ |
| 6 | что такое MRR | сложное | ✗ | ✗ | ✓ |
| | **пройдено** | | **4/6** | **5/6** | **6/6** |

Скорость, выдача токенов:

| где | ток/с | холодный старт |
|---|---|---|
| `qwen2.5:3b` | **82** | 0.62с |
| `qwen2.5:7b` | 45 | 1.57с |
| облако (DeepSeek) | 42 | — |

Трёхмиллиардная модель на ноутбуке выдаёт токены **вдвое быстрее облака**
и вдвое чаще ошибается. Это и есть размен.

### Чем ошибаются локальные модели

**3B написала «Токyo»** — три знака кириллицей, два латиницей. Ответ по
смыслу верный, но в таком виде его не распарсить и не показать человеку.
У 7B этого нет.

**И 3B, и 7B уверенно отвечают, что MRR — это Monthly Recurring Revenue.**
Не «не знаю», а подробное объяснение не того. Размер модели это не
исправил, и это самое интересное наблюдение дня.

## Главный опыт: незнание лечится не размером

Если модель не знает ответа — дайте ей документы. Проверка на трёх
вопросах, где локальная модель заведомо не в курсе:

```bash
python3 with_rag.py
```

```
режим            верных ответов
без RAG                 0/3
с RAG                   3/3
```

На том же `qwen2.5:3b`:

```
БЕЗ RAG: MRR, или Monthly Recurring Revenue, в контексте оценки
         поисковых систем обычно относится к показателю, который
         оценивает средний размер ежемесячного дохода…

С RAG:   MRR (Mean Reciprocal Rank) в оценке поисковых систем
         представляет собой среднее значение 1/расстояния до первого
         положительного результата для каждого запроса.
         источник: days/day-21-indexing/README.md#structural#5
```

Цитаты проверяются ровно тем же кодом, что в дне 24, — и он поймал одну
выдуманную цитату у локальной модели. Проверка дословности не зависит
от того, кто написал текст.

Отсюда практический вывод: маленькая модель на ноутбуке не знает фактов,
но **умеет читать**. Со своим поиском она закрывает разрыв в знаниях —
бесплатно, без сети и без отправки документов наружу.

## Тот же чат, но без сети

Окно не стенд с кнопками, а чат из дня 25 — с историей, раскрытием
уточнений, источниками и памятью задачи. Целиком на локальной модели:
провайдер прокинут во все три обращения, иначе половина диалога уходила
бы в сеть и «локально» было бы неправдой.

```
вы › Какая стратегия нарезки документов победила в сравнении?
      Стратегия нарезки по структуре победила: MRR 0.774 против 0.449.
      источник: days/day-21-indexing/README.md#structural#5

вы › А на сколько именно?
      искал: На сколько именно стратегия нарезки по структуре превосходит
             стратегию нарезки по размеру в метрике MRR
      Превосходит на 0.325.
```

### Где локальная модель всё-таки проигрывает

**Раскрытие уточнений маленькой модели даётся с трудом.** Первый прогон
чата на 3B дал вот что: на «А на сколько именно?» запрос превратился
в «сколько стоит сжатие истории диалога в токенах» — совсем другая тема.
То же самое выдала и 7B, слово в слово.

Одинаковая ошибка у двух разных моделей — это не случайность. Причина
нашлась в моём же промпте: в нём стоял конкретный пример,

> «Сколько именно?» после разговора о цене сжатия должно стать
> «сколько стоит сжатие истории диалога в токенах»

и локальные модели **списывали пример дословно** вместо того, чтобы
применить образец. Облачная обобщала. После замены примера на схематичный
(«если говорили про ПРЕДМЕТ, а потом спросили «а почему?»…») все три
модели стали раскрывать правильно.

Урок общий: few-shot пример для маленькой модели — не подсказка,
а шаблон для копирования. Заодно починился и день 25.

**Дословные цитаты — слабое место.** Замер на четырёх вопросах:

| модель | цитат дано | подтверждено дословно | выдумано |
|---|---|---|---|
| `qwen2.5:3b` | 4 | 2 (50%) | 2 |
| `qwen2.5:7b` | 4 | 1 (25%) | 3 |
| облако | 14 | **14 (100%)** | 0 |

Локальные модели дают цитат втрое меньше и половину из них пересказывают
вместо копирования. То есть защита от выдумок из дня 24 на них почти
не работает — проверка честно это показывает, но пользы от неё мало,
когда подтверждать нечего.

Вывод без прикрас: локальная модель годится **отвечать по документам**,
но не годится **доказывать цитатами**. Если цитаты важны, нужна модель
крупнее или облако.

**Реранкинг на локальной модели работает, и 3B здесь лучше 7B.**
Неожиданный результат на вопросе про наверстывание:

| где переупорядочивать | нужный кусок | оценено моделью | время |
|---|---|---|---|
| без реранкинга | не найден | — | 0.7с |
| `qwen2.5:3b` | **2-е место** | 5 из 5 | 6.5с |
| `qwen2.5:7b` | не найден | 2 из 5 | 8.3с |
| облако | 1-е место | 5 из 5 | 1.4с |

Семимиллиардная модель вернула неполный JSON и оценила только два куска
из пяти. На структурированном выводе больше не значит лучше.

Реранкинг в чате включён, хотя и стоит около шести секунд на реплику
вместо одной: без него локальный чат чаще отказывается отвечать.

## Два дефекта, которые нашлись при сборке чата

**Второй этап уходил в облако.** `retrieve()` из дня 23 не принимал
провайдера, поэтому реранкинг запроса шёл к DeepSeek, даже когда весь
остальной чат работал локально. Утверждение «всё локально» было бы
неправдой. Теперь провайдер прокинут в `rerank_query`, `rerank_with_llm`
и `retrieve`.

**Токены второго этапа не считались.** `Reply.total_tokens` складывал
ответ, раскрытие уточнения и память задачи, а реранкинг — нет. В окне
стояла одна и та же цифра независимо от того, включён он или выключен.
Сейчас видно: без реранкинга 2285 токенов на реплику, с ним 4823.

**И отдельно — то, что дефектом не оказалось.** Локальный чат отказывался
отвечать про наверстывание даже с реранкингом. Я полез искать ошибку
и нашёл, что ошибки нет: поиск по фразе «наверстывание в планировщике»
возвращает куски про переходы задач из дней 13 и 15, а нужного раздела
в двадцати найденных вообще нет. Реранкинг чинит точность, а не полноту —
переупорядочивать нечего. Отказ был правильным поведением.

## Мелочи, которые всплыли в работе

**Опечатка в собственном тесте.** В промпте про яблоки у меня оказался
китайский иероглиф 三 вместо «3». Модель 3B справилась, 7B запуталась
и стала решать с неизвестным `x`. Полчаса я думал, что это деградация
большой модели, пока не перечитал промпт.

**Замер холодного старта врал.** Первая версия печатала «первый запрос
0.11с — в нём загрузка модели»: модель уже была в памяти с прошлого
прогона. Настоящая загрузка — 0.62с. Теперь холодный старт мерится
флагом `--cold`, который сначала выгружает модель через `ollama stop`.

**Имя локальной модели уезжало в облако.** Окно всегда шлёт выбранную
слева модель, и при галочке «в облаке» DeepSeek отвечал:

```
HTTP 400: The supported API model names are deepseek-flash,
deepseek-v4-pro, but you passed qwen2.5:3b
```

Отсекается теперь на сервере, в одной функции на все четыре маршрута,
а не в окне: надеяться на клиент в таком месте не стоит.

**Ollama в бандл не положить.** Это отдельная программа плюс модель на
гигабайты. Приложение только проверяет, что сервер отвечает, и подсказывает
команды, если нет.

**Место на диске.** На машине было свободно 28 ГБ, после двух моделей
осталось 21 ГБ. Для 3B хватает и десяти.

## Запуск

Один раз:

```bash
brew install ollama
ollama serve &                 # или: brew services start ollama
ollama pull qwen2.5:3b
```

Потом:

```bash
cd days/day-26-local-llm

ollama run qwen2.5:3b "Привет! Кто ты?"     # самый короткий путь
python3 probe.py --cold                      # шесть запросов с замером
python3 probe.py --cloud                     # то же в облаке
python3 with_rag.py                          # с нашими документами
python3 web.py                               # http://127.0.0.1:8000
./build_app.sh && open "dist/День 26.app"
```

Проверить руками, что сервер жив:

```bash
curl -s http://127.0.0.1:11434/api/version
curl -s http://127.0.0.1:11434/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen2.5:3b","messages":[{"role":"user","content":"Скажи: работает"}]}'
```

Для `with_rag.py` нужен индекс дня 21. Если его нет:

```bash
cd ../day-21-indexing && python3 build.py
```
