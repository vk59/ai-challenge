# День 34 — ассистент для файлов проекта

Задаёте цель, ассистент сам выбирает файлы и работает с ними через настоящий
MCP stdio: обнаруживает структуру, ищет текст, читает исходники, готовит изменения
и unified diff. С `--apply` изменения действительно сохраняются.
Python 3.10+, стандартная библиотека; зависимости устанавливать не нужно.

## Веб-интерфейс для видео

```bash
python3 days/day-34-files/web.py
# Без ключа, тот же интерфейс и настоящий MCP:
python3 days/day-34-files/web.py --demo
```

Откройте **http://127.0.0.1:8034**. Выберите пример или задайте свою цель,
нажмите **«Подготовить diff»**. Видны реальные шаги MCP, прочитанные файлы,
результат и цветной unified diff. **«Сохранить изменения»** записывает именно
показанные предложения без повторного вызова модели. Изменившийся файл вызывает
конфликт: внешние правки не перезаписываются. Вкладка «Файл» показывает сохранённое
содержимое; «Журнал MCP» — последовательность инструментов.

При каждом запуске создаётся новая учебная копия в `memory/day34-web/<id>/`.
Для своего проекта: `--project /absolute/project/path`; порт: `--port 8034`.
Ключ и `DAY34_MODEL` настраиваются так же, как для CLI ниже.
Сервис слушает только loopback, проверяет Host/Origin, ограничивает тело запроса
и хранит до 8 задач в памяти. После перезапуска preview нужно подготовить заново.
Запись атомарна для каждого файла, общей транзакции для нескольких файлов нет.

HTTP API: `GET /api/project`, `GET /api/file?path=...`, `POST /api/tasks`
с `{"goal":"..."}`, `GET /api/tasks/<id>`,
`POST /api/tasks/<id>/apply` с `{}`. Смена корня проекта через API запрещена.

Проверка обоих сценариев через HTTP (в отдельной временной копии):
`python3 days/day-34-files/web_smoke.py --live`.

## Быстрый запуск CLI

Из корня репозитория:

```bash
# Без ключа: детерминированный демонстрационный план, настоящий MCP
python3 days/day-34-files/assistant.py --demo \
  --goal 'Найди все использования login и создай отчёт'

# Сохранить отчёт в учебный проект
python3 days/day-34-files/assistant.py --demo --apply \
  --goal 'Найди все использования login и создай отчёт'

# Второй сценарий: изменить существующую документацию по исходникам
python3 days/day-34-files/assistant.py --demo --apply \
  --goal 'Обнови документацию по входу на основе кода, сохрани остальные разделы'
```

По умолчанию пример из `sample/` копируется в `memory/day34-project/` один раз.
Исходные фикстуры не меняются; последующие запуски работают с этой же копией.
В выводе видны абсолютный корень, прочитанные файлы, MCP-вызовы, diff и отдельно
`Saved`. Preview не создаёт даже каталог `reports`; `--apply` разрешает запись.
Повторное применение демо даёт пустой diff. Для нового прогона используйте новую
копию `sample/` через `--project`; автоматического удаления проекта нет.

## Настоящий AI-режим

По умолчанию используется **DeepSeek напрямую**, без OpenRouter.
`--provider openrouter` в CLI или веб-сервере явно включает старый провайдер
с отдельным ключом `OPENROUTER_API_KEY`; его модель по умолчанию —
`deepseek/deepseek-chat`. Для прямого DeepSeek модель — `deepseek-chat`.


Задайте `DEEPSEEK_API_KEY` в окружении или корневом `.env`, уберите `--demo`:

```bash
python3 days/day-34-files/assistant.py --apply \
  --goal 'Найди все использования API login и создай отчёт с файлами и строками'
```

Модель `deepseek-chat` сама выбирает инструменты и пути. Она получает
только цель и схемы MCP; исходники не подставляются заранее из известных файлов.
`DAY34_MODEL` меняет модель; `AI_ADVENT_ENV_FILE` указывает иной файл окружения,
например `.env` основного checkout при работе в worktree. Ключ не показывается
модели и не печатается в лог. Без ключа AI-режим завершается ошибкой.

Для своего проекта укажите `--project /absolute/project/path`. Без `--apply`
изменения остаются только в diff. `--output /tmp/file-task.json` сохраняет
отдельный JSON-отчёт с diff, trace и перечнями прочитанных/изменённых файлов.
Этот путь экспорта задаёт оператор, а не модель.

## Два сценария

| Цель | Файлы, которые исследует ассистент | Результат |
|---|---|---|
| Найти использования `login` | `src/auth.py`, `src/web.py`, `src/cli.py` | Новый отчёт в `reports/` с файлами и строками |
| Обновить документацию входа | исходники и `docs/auth.md` | Актуальная сигнатура, `mfa_code`, поля ответа и `expires_in=3600`; остальные разделы сохранены |

Демо использует AST исходников и результаты MCP-поиска; это явно обозначенный
детерминированный режим без LLM, ограниченный двумя учебными сценариями. В AI-режиме
план и содержимое документов создаёт реальная модель через цикл tool calling.

## Файловый протокол

```text
цель → модель → list_files / search_text / read_file
     → propose_file → show_diff → отчёт
                              → --apply → apply_changes → сохранённые файлы
```

Сервер запускается клиентом: `python3 server.py --project PATH`.
Модели доступны пять инструментов; `apply_changes` ей не передаётся.
Сервер включает его только с `--allow-apply`, который передаёт CLI при `--apply`.
Успех требует трёх реально прочитанных файлов и успешного `propose_file`.
Одного ответа модели «всё готово» недостаточно.

## Ограничения и сохранение

- Корень фиксирован на старте. Выход через `..`, абсолютные пути и symlinks запрещён.
- Читаются текстовые исходники; скрытые/секретные/бинарные/generated файлы исключены.
  `reports/` не участвует в поиске, чтобы отчёт не находил сам себя при повторе.
  Поиск возвращает `truncated` и `skipped`; результаты не объявляются полными при пропусках.
- Записывается только Markdown в `docs/`, `reports/`, корневые README/CHANGELOG.
  Перед изменением существующего файла обязателен `read_file`.
- Перед записью проверяются исходные SHA всех изменений. При конфликте до начала
  записи ничего не применяется. Замена каждого файла атомарна; общей транзакции
  нескольких файлов нет. Ошибка после частичного применения содержит `applied_files`.
- Нет shell-команд, удаления, импорта или исполнения кода проекта. Файлы передаются
  модели как недоверенные данные. Фильтр секретов эвристический: в AI-режиме используйте
  только разрешённые для отправки провайдеру исходники.

Лимиты: 300 файлов на сканирование, 80 совпадений, чтение файла до 64 КБ;
5 предложенных файлов по 20000 символов, 50000 суммарно; 12 раундов и 30 вызовов
инструментов, 160000 символов результатов инструментов; цель до 2000 символов.

## Проверки

```bash
python3 -m unittest discover -s days/day-34-files -p 'test_*.py' -v
python3 days/day-34-files/smoke.py
python3 days/day-34-files/smoke.py --live --output /tmp/day34-evidence
```

Unit-тесты запускают реальный MCP, модель заменена моками. Smoke проверяет два
сценария на временной копии, сохранённые файлы, исходники без изменений и отсутствие
повторного diff в демо. `--live` использует настоящую платную модель и проверяет
её реальные tool calls. В CI доступны trace/diffs и итоговый проект в artifact
`day34-file-work-evidence`; облачная проверка запускается только для same-repo PR.
