# День 11 — Модель памяти агента

## Задание

Описать и реализовать модель памяти: минимум три типа (краткосрочная, рабочая,
долговременная), хранить их отдельно, явно выбирать, что и куда сохраняется.
Проверить, какие данные попадают в каждый слой и как это влияет на ответы.

## Модель

Слои различаются **не форматом, а областью жизни**. Это единственный критерий,
по которому их вообще имеет смысл разделять:

| слой | что хранит | где лежит | область | когда умирает |
|---|---|---|---|---|
| **Краткосрочная** | реплики диалога | `turns` + окно в памяти | сессия | вытесняется окном |
| **Рабочая** | данные текущей задачи | `facts` | сессия | вместе с задачей |
| **Долговременная** | профиль, решения, знания | `longterm` | **все диалоги** | только вручную |

Если бы все три лежали в сессии, разделение было бы косметическим. Поэтому
в таблице `longterm` **нет колонки `session`** — и это главное техническое
отличие слоя:

```sql
CREATE TABLE longterm (
    key    TEXT PRIMARY KEY,   -- ключ уникален глобально, не в пределах сессии
    value  TEXT NOT NULL,
    kind   TEXT NOT NULL,      -- profile | decision | knowledge
    source TEXT                -- из какого диалога приехало
);
```

Долговременная делится на три подтипа, как просит задание: **профиль** (кто
человек, как с ним общаться), **решения** (что постановили, действует дальше),
**знания** (устойчивые факты о продукте).

## Что происходит на практике

Одна реплика — и агент раскладывает её по слоям:

> «Меня зовут Иван, пишу на Python. Бюджет проекта 800 тысяч, срок 3 месяца.
> Решили брать PostgreSQL 16.»

```
рабочая +5:        бюджет, срок, стек, СУБД, статус
долговременная +3: имя, язык, СУБД
```

Разложилось так:

```
● Рабочая — область: диалог «default»
   бюджет: 800 тысяч
   срок: 3 месяца
   СУБД: PostgreSQL 16

● Долговременная — область: все диалоги
   ── профиль
   имя: Иван            ← default
   язык: Python         ← default
   ── решения
   СУБД: PostgreSQL 16  ← default
```

**Бюджет и срок — рабочие**: они про эту задачу и умрут вместе с ней.
**Имя и язык — профиль**: пригодятся в любом разговоре. **Выбор СУБД —
решение**: оно действует и дальше, поэтому попало в оба слоя. Это не дубль,
а разный смысл: в рабочей — параметр задачи, в долговременной — принятое
решение.

### Как это влияет на ответы

Открываем **другой диалог** и спрашиваем то же самое:

```
диалог «другая-задача» · краткосрочная 0 пар · рабочая 0 · долговременная 3
Агент вас уже знает: 3 записей из прошлых диалогов.

вы › Как меня зовут и какой бюджет?
помощник › Тебя зовут Иван.
           Про бюджет — таких данных нет (есть только имя, язык Python
           и решение по СУБД — PostgreSQL 16).
```

Имя помнит, бюджет — нет. Ровно как задумано: профиль переехал, данные
задачи остались в прошлой задаче. Это и есть проверка модели памяти —
не «помнит всё» и не «забыл всё», а **помнит то, что должен помнить**.

## Явный выбор, что куда

Раскладку делает модель — один запрос после каждой реплики возвращает JSON
с двумя ключами, `working` и `long`. Критерий в промпте один: **переживёт ли
факт текущую задачу**.

Но автоматика ошибается, поэтому есть и ручной способ — иначе «модель памяти»
превращается в чёрный ящик:

```bash
/запомнить профиль имя=Иван
/запомнить решение бд=PostgreSQL 16
/запомнить рабочая бюджет=800 тысяч
/забыть бюджет
```

В окне то же самое — поля ввода прямо под каждой панелью, и крестик на любой
записи долговременной памяти.

Попытка записать в краткосрочную даёт внятную ошибку: туда писать нельзя,
краткосрочная память — это сами реплики, а не карточки.

## Приложение

День сделан как окно, а не как скрипт, потому что слои надо **видеть**.

```bash
cd days/day-11-memory-model
python3 web.py              # http://127.0.0.1:8000
./build_app.sh && open "dist/День 11.app"
python3 cli.py              # то же самое в терминале
```

Справа три панели с разными цветами. Под каждой — её область жизни. Когда
агент что-то запоминает, запись подсвечивается, а под ответом появляется
`рабочая: +2 · долговременная: +1`.

В заголовке — список диалогов и две разные кнопки, и путать их нельзя:

| кнопка | что делает | что с памятью |
|---|---|---|
| **Новый диалог** | создаёт новую сессию | старый диалог цел на диске, в новом краткосрочная и рабочая пустые, **долговременная переехала** |
| **Стереть** | стирает текущую сессию | краткосрочная и рабочая гибнут, долговременная цела |

Главная проверка дня — именно **«Новый диалог»** с возвратом через список:
уходим в новый диалог (агент помнит имя, но не помнит бюджет), возвращаемся
в старый — бюджет на месте.

Измерено на живом сервере:

```
исходный диалог          краткосрочная 3 | рабочая 2 | долговременная 2
→ новый диалог           краткосрочная 0 | рабочая 0 | долговременная 2
→ вернулись в старый     краткосрочная 3 | рабочая 2 | долговременная 2
→ «Стереть»              краткосрочная 0 | рабочая 0 | долговременная 2
```

## Что сломалось при первом же настоящем использовании

Три дефекта, найденных не в тесте, а в живой работе с приложением.

**Переключения диалогов не было вовсе.** Кнопка называлась «Новый диалог»,
а вызывала `/reset`, который стирает текущую сессию и **остаётся в ней же**.
Сессия всегда была одна — `default`. То есть заявленную проверку слоёв
(«долговременная переживает смену диалога») приложение выполнить не могло:
менять было не на что. Добавлены роут `/session`, список диалогов в заголовке
и отдельная кнопка «Стереть».

**Роутер записал мету про самого агента — и это отравило все ответы.**
В долговременной памяти оказалось:

```
knowledge | запись в долговременную память |
  у ассистента нет инструмента самостоятельной записи в долговременную
  память; сохранение между сессиями возможно только на стороне приложения
```

Модель сочинила это про себя, запись попала в `knowledge` и с тех пор
уезжала в **каждый** запрос. Результат — агент начал приписывать к ответам
оговорку «это я знаю из контекста текущей сессии, сам в память не пишу».
Он сам себя убедил, что памяти у него нет.

**Роутер пишет заглушки и служебную мету.** `валюта: не указана`,
`охват бюджета: не указан`, `текущий вопрос: пользователь проверяет…`,
`статус: ждём уточнения`. Плюс дубли одного смысла: `стек` и `язык` — оба
`Python`. Всё это раздувает промпт и ничего не даёт.

Последние два лечатся прямым запретом в промпте роутера:

```
ЗАПРЕЩЕНО записывать:
- что-либо про самого ассистента, его устройство, память или возможности;
- значения-заглушки: «не указано», «неизвестно», «нет данных»;
- служебную мету о ходе разговора: «текущий вопрос», «статус»;
- один и тот же смысл под разными ключами.
```

Полностью это не лечится — модель всё равно иногда сочиняет, поэтому панели
показывают содержимое памяти, а крестик рядом с каждой записью её удаляет.
**Память агента должна быть видимой и правимой руками** — это, пожалуй,
главный практический вывод дня.

## Остальные особенности

**Раскладка стоит отдельного запроса** на каждую реплику — как извлечение
фактов в дне 10. В статусной строке это отдельная цифра «служебных».

**`reset()` намеренно не трогает долговременную память.** «Стереть диалог»
не должно означать «забыть человека». Для этого есть `forget()`.
