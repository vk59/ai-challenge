# День 32 — спецификация: автоматическое AI-ревью PR

## Цель

Добавить в AI Advent Challenge самостоятельный пример автоматического ревью кода. При открытии или обновлении pull request GitHub Actions собирает diff и содержимое изменённых файлов, извлекает релевантный контекст из кода и документации репозитория через RAG, просит LLM подготовить ревью и публикует результат в PR.

## Пользовательский результат

Автор PR получает комментарий с тремя разделами:

1. потенциальные баги и ошибки корректности;
2. архитектурные проблемы и риски поддержки;
3. конкретные рекомендации.

Для каждого замечания указываются файл и строка, если их можно достоверно определить. Если замечаний нет, ассистент явно сообщает об этом и кратко описывает проверенный объём. Ревью не должно выдавать предположение за подтверждённый баг.

## Предлагаемая структура

- `.github/workflows/day-32-review.yml` — запуск на `pull_request` при открытии, повторном открытии и `synchronize`; минимальные права `contents: read` и `pull-requests: write`.
- `review.py` — сбор diff/изменённых файлов, построение временного индекса контекста, запрос к модели и формирование Markdown.
- `corpus.py` — сбор безопасного текстового корпуса Markdown-документов и исходного кода репозитория с исключением секретов, бинарных и генерируемых файлов.
- `README.md` — архитектура, локальный запуск, настройка секретов GitHub и ограничения.
- `video.md` — короткий сценарий демонстрации PR и автоматического комментария.

Переиспользовать `shared/index.py` и `shared/embeddings.py` для RAG, а `shared/llm.py` — для генерации. Индекс хранить во временном каталоге одного запуска Actions. Изменённые файлы и diff получить из PR head; корпус для поиска брать из base-версии, чтобы ответы не подменяли исходный контекст версиями из самого изменения.

## Безопасность и отказоустойчивость

- Запускать `pull_request`, не `pull_request_target`; не исполнять код из PR.
- Рассматривать diff, исходники и найденные фрагменты как недоверенные данные, а не инструкции для ассистента.
- Не включать `.env`, ключи, бинарные файлы, lock/cache/build-артефакты в diff-контекст или индекс.
- Не печатать API-ключи и полный запрос/ответ с потенциально чувствительным содержимым в логи.
- Неизвестный формат ответа, отсутствие ключа/модели, слишком большой diff и ошибки GitHub API должны завершать job понятным сообщением, не публикуя выдуманное ревью.
- Секреты GitHub Actions недоступны workflow для PR из fork; в README описать это ограничение и способ запуска для таких PR после проверки владельцем.

## Вне объёма

- Автоматически отклонять PR, ставить blocking review или менять код.
- Автоматически исправлять замечания.
- Поддерживать внешние репозитории и сторонние Git-платформы.
- Гарантировать полноту или истинность выводов LLM.

## Критерии готовности

- Workflow запускается на открытие и обновление PR.
- Ассистент получает diff и список изменённых файлов с содержимым.
- Retrieval действительно использует контекст Markdown и кода из базовой версии репозитория.
- Комментарий содержит разделы багов, архитектурных проблем и рекомендаций, а замечания привязаны к строкам только при наличии точного соответствия.
- Документация объясняет секреты, локальный запуск, fork-ограничение и сценарий видео.
